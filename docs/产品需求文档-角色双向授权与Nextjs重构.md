## 2. 产品定位

`叩饭（Cofounder）` 是一个连接“项目方 / 行业专家”与“程序员”的合伙协作平台。

平台核心不是传统招聘，也不是外包撮合，而是帮助双方在低门槛建立联系后，通过更完整的信息展示与双向授权机制，逐步进入更深层沟通，最终推动合作、共创 MVP。

核心理念：

- 不是雇佣，是协作与合伙
- 先用最少信息建立连接，再在需要时补充更多信息
- 任何一方都不应该在未明确授权前暴露自己的详细信息与联系信息

## 3. 产品目标

### 3.1 业务目标

- 让项目方可以低成本发布项目需求与自身背景
- 让程序员可以低成本展示技能、项目经历与合作兴趣
- 让未登录用户也能看到足够的基础信息，形成供需流动
- 让“收藏、点赞、了解详情”等深度互动建立在登录与授权基础上
- 让双方通过渐进式信息填写与双向确认，减少沟通成本与信任风险

### 3.2 体验目标

- 首次录入只收集最少必要信息，降低填写阻力
- 详细信息只需要填写一次，并在需要时复用
- 用户在每一步都能明确知道：
  - 对方现在能看到什么
  - 对方现在还看不到什么
  - 点击下一步后会新增暴露什么信息

### 3.3 当前阶段范围

本阶段仅完成：

- 新的统一 PRD 文档
- `README.md` 更新
- 对旧文档做废弃处理

本阶段不包含：

- Next.js 项目初始化
- Taro 代码迁移
- NestJS 接口改造
- 数据库结构调整
- 实际页面开发

## 4. 技术重构方向

### 4.1 前端

目标前端技术栈：

- `Next.js v16`
- `React`
- 推荐采用 `App Router`
- 前端职责聚焦于：
  - 公共浏览页面
  - 登录与用户中心
  - 资料录入与分步补全
  - 收藏 / 点赞 / 了解详情 / 请求处理 / 联系信息交换

### 4.2 后端

后端保持：

- `NestJS`
- 继续作为统一业务 API 服务
- 继续承载认证、用户资料、关系请求、权限校验、通知等逻辑

### 4.3 重构原则

- 前后端职责边界不因前端替换而改变
- 先明确产品状态机与信息可见规则，再进入开发
- 不把旧 Taro 页面结构直接照搬到 Next.js，而是按新的业务流程重组页面与路由

## 5. 角色与账号规则

### 5.1 角色定义

平台分为两种角色：

- **项目方 / 行业专家**
  - 发布项目基础信息
  - 补充个人与项目详细背景
  - 接收来自程序员的“了解详情”请求
  - 决定是否向对方开放自己的详细信息与后续联系信息交换资格

- **程序员**
  - 发布个人技能与项目经验基础信息
  - 补充个人详细背景
  - 向项目方发起“了解详情”请求
  - 在获得项目方同意后进一步申请交换联系信息

### 5.2 账号规则

结合历史方案与当前需求，MVP 阶段建议采用：

- 一个账号只对应一个角色
- 注册后角色不可直接切换
- 如果未来要支持双身份，另行设计，不纳入本次重构范围

### 5.3 发布者与意向者定义

在“了解详情”流程中：

- **发布者**：当前这条信息的发布人
  - 可能是项目方
  - 也可能是程序员
- **意向者**：想进一步了解发布者并尝试建立联系的人
  - 可能是项目方
  - 也可能是程序员

本期核心主流程优先支持：

- 程序员对项目方发起请求

但产品规则设计应保持双向通用，为后续支持“项目方主动了解程序员”预留一致机制。

## 6. 信息架构

平台中的信息分为三层：

- **基础信息**：未登录用户即可浏览
- **详细信息**：需要进入授权流程后，按规则逐步可见
- **联系信息**：最敏感信息，必须经过双向确认后才可交换或查看

### 6.1 项目方信息结构

#### 6.1.1 基础信息

项目方基础信息只要求填写 2 项：

| 字段 | 必填 | 说明 | 可见范围 |
|------|------|------|----------|
| 项目描述 | 是 | 对项目做最基础说明 | 未登录用户可见 |
| 所在城市 | 是 | 项目方所在城市 | 未登录用户可见 |

#### 6.1.2 详细信息

项目方详细信息包括：

| 模块 | 字段 |
|------|------|
| 个人简介 | 个人介绍 |
| 教育背景 | 学校、专业 |
| 工作背景 | 公司、做过哪些事 |
| 项目详情 | 对项目的进一步描述 |
| 联系方式 | 电话、微信、QQ、邮箱等，均为选填 |

说明：

- 详细信息只需要填写一次
- 联系方式虽属于详细信息的一部分，但其展示权限独立受控
- 即使详细信息已被对方查看，联系方式仍不能自动被看到

### 6.2 程序员信息结构

#### 6.2.1 基础信息

程序员基础信息只要求填写 3 项：

| 字段 | 必填 | 说明 | 可见范围 |
|------|------|------|----------|
| 会哪些技能及做过哪些项目 | 是 | 对技能与过往项目做简要说明 | 未登录用户可见 |
| 想做什么方向 / 类型的项目 | 否 | 合作偏好 | 未登录用户可见 |
| 所在城市 | 是 | 当前所在城市 | 未登录用户可见 |

#### 6.2.2 详细信息

程序员详细信息包括：

| 模块 | 字段 |
|------|------|
| 个人简介 | 个人介绍 |
| 教育背景 | 学校、专业 |
| 工作背景 | 公司、做过哪些事 |
| 做过的产品 / 项目介绍 | 代表作品、参与项目说明 |
| 联系方式 | 电话、微信、QQ、邮箱等，均为选填 |

说明：

- 详细信息只需要填写一次
- 联系方式默认不暴露，必须单独经过联系交换流程

### 6.3 联系方式规则

联系方式字段包含但不限于：

- 电话
- 微信
- QQ
- 邮箱

规则如下：

- 在填写详细信息时，这些字段都可以不填
- 但当用户走到“同意后准备交换联系方式”或“真正交换联系方式”时，必须至少补充并选择 1 个联系方式
- 联系方式的选择是一次具体授权动作，而不是“只要填过就自动对外可见”

## 7. 权限与可见性规则

### 7.1 未登录用户

未登录用户可以：

- 浏览项目方基础信息
- 浏览程序员基础信息

未登录用户不可以：

- 收藏
- 点赞
- 发起“了解详情”
- 查看任何详细信息
- 查看任何联系方式

### 7.2 已登录用户

已登录用户可以：

- 收藏
- 点赞
- 发起“了解详情”请求
- 管理自己发出的请求与收到的请求
- 填写自己的基础信息与详细信息

### 7.3 发布者查看意向者信息时

发布者收到“了解详情”请求后：

- 可以直接看到意向者的基础信息
- 可以直接看到意向者详细信息的打码版本
  - 目的是让发布者知道对方是否认真填写了大量信息
  - 但在未达成条件前，不能看到具体内容
- 不能直接看到意向者的联系方式

### 7.4 意向者查看发布者信息时

意向者在发布者同意之前：

- 只能看到发布者基础信息
- 不能看到发布者详细信息
- 不能看到发布者联系方式

意向者在发布者同意之后：

- 可以看到发布者详细信息
- 仍然不能直接看到发布者联系方式
- 若要看到发布者联系方式，必须再进入“交换联系信息”流程

### 7.5 自己不能了解自己

- 发布者不能对自己发布的信息发起“了解详情”
- 前端应直接隐藏或禁用入口
- 后端仍必须做最终校验，防止绕过前端

## 8. 核心流程

## 8.1 总体流程概览

### 8.1.1 浏览与轻互动

1. 未登录用户进入平台
2. 浏览项目方与程序员的基础信息
3. 如需收藏、点赞、了解详情，则要求先登录

### 8.1.2 深度了解与授权

1. 用户登录后可以收藏、点赞
2. 用户点击“了解详情”时，如果自己的详细信息未填写，则先引导补全
3. 意向者发出请求后，发布者收到请求并处理
4. 发布者先查看意向者的基础信息和被打码的详细信息
5. 发布者在满足条件后查看意向者未打码的详细信息（但不含联系方式）
6. 发布者决定同意或拒绝
7. 若同意，意向者可看到发布者详细信息（但不含联系方式）
8. 意向者若要进一步联系，再进入“交换联系信息”流程

---

## 8.2 “了解详情”按钮设计要求

“了解详情”不是普通轻互动，应比收藏、点赞明显很多。

设计要求：

- 按钮视觉层级明显高于收藏、点赞
- 可以与收藏、点赞放在不同区域
- 在列表页与详情页都要突出
- 文案需明确表达其含义是“申请查看更完整信息”，而不是立即私聊

建议：

- 收藏、点赞使用次级按钮或图标按钮
- “了解详情”使用主按钮
- 在按钮附近附带说明：
  - 申请后需对方同意
  - 联系方式不会立即展示

---

## 8.3 意向者发起“了解详情”请求

### 8.3.1 前置条件

意向者点击“了解详情”时，系统依次检查：

1. 是否已登录
2. 是否是自己查看自己
3. 是否已填写详细信息

### 8.3.2 详细信息拦截逻辑

如果意向者还没有填写详细信息：

- 不允许直接发送请求
- 弹出明确说明：
  - 详细信息只需要填写一次
  - 这样做是为了让对方更好地了解自己，减少沟通与判断成本
  - 这些信息只有在对方授权流程中才会按规则被看到
  - 联系方式只有在进一步授权后才会展示
- 引导意向者先完成详细信息填写

如果意向者已经填写过详细信息：

- 可以直接发送“了解详情”请求

### 8.3.3 请求提交结果

请求发送成功后：

- 进入“待发布者处理”状态
- 发布者会收到站内通知 / 请求列表提醒
- 意向者在此阶段仍看不到发布者详细信息与联系方式

---

## 8.4 发布者处理“了解详情”请求

### 8.4.1 发布者默认可见内容

发布者收到请求后，可以看到：

- 意向者基础信息
- 意向者详细信息的打码版本
  - 应通过段落骨架、字段结构、字数占位等方式体现“内容很多”
  - 不能泄露具体文本内容
- 请求时间与请求状态

### 8.4.2 “查看对方详细信息”按钮

发布者如要查看意向者未打码的详细信息，需要点击 `查看对方详细信息` 按钮。

触发规则：

- 系统先检查发布者自己是否已经填写详细信息
- 如果未填写：
  - 不允许查看
  - 引导发布者先填写自己的详细信息
- 如果已填写：
  - 允许查看意向者的详细信息正文
  - 但不能查看意向者的联系方式

说明：

- 该动作代表“我愿意先认真看对方更完整的信息”
- 这是发布者后续做同意 / 拒绝判断的前置动作

### 8.4.3 同意 / 拒绝前置条件

发布者在点击“同意”或“拒绝”前，必须先完成一次 `查看对方详细信息`。

也就是说：

- 没有先查看未打码详细信息，就不能直接同意或拒绝
- 这样可以减少机械性处理请求，提高反馈质量

### 8.4.4 拒绝流程

如果发布者拒绝：

- 必须填写拒绝理由
- 拒绝后：
  - 意向者看不到发布者详细信息
  - 意向者看不到发布者联系方式
  - 意向者能收到拒绝结果与理由

### 8.4.5 同意流程

如果发布者同意：

- 意向者可以看到发布者的详细信息
- 但此时仍看不到发布者联系方式

在点击“同意”时，需要出现一个弹框，用于让发布者处理自己的联系方式授权设置。

弹框要求：

- 从发布者已经填写过的联系方式中列出可选项
- 若一个都没有，则允许在弹框中直接新增联系方式，并回填到详细资料中
- 发布者至少选择 1 个联系方式，作为后续可交换的联系方式
- 要明确提示：
  - 此时并不是立即把联系方式展示给意向者
  - 只有当意向者后续点击“交换联系信息”并提交自己的联系方式后，发布者选中的联系方式才会真正对其可见

这样设计的原因：

- 与你的要求保持一致：意向者在“同意后”先看到的是详细信息，不是联系方式
- 同时保留发布者对未来联系方式交换的主动授权与选择权

---

## 8.5 意向者收到同意 / 拒绝结果后的流程

### 8.5.1 收到拒绝

意向者可以看到：

- 发布者已拒绝
- 拒绝理由

意向者不可以看到：

- 发布者详细信息
- 发布者联系方式

### 8.5.2 收到同意

意向者可以看到：

- 发布者详细信息

意向者仍不可以看到：

- 发布者联系方式

此时页面应出现更明确的下一步主按钮：`交换联系信息`

按钮说明必须非常清楚：

- 点击后，你需要把自己的联系方式发送给对方
- 完成后，你才能看到对方授权给你的联系方式

---

## 8.6 “交换联系信息”流程

### 8.6.1 触发时机

意向者只有在以下条件都满足时，才可点击 `交换联系信息`：

- 发布者已同意其“了解详情”请求
- 意向者已具备详细信息
- 发布者已在同意环节选择可交换联系方式

### 8.6.2 弹框内容

点击后弹出表单：

- 展示意向者自己已有的联系方式
- 允许意向者勾选 1 个要发送给发布者的联系方式
- 如果没有，则允许在弹框中新增，并回填到自己的详细资料中

### 8.6.3 完成后的结果

提交成功后：

- 发布者收到意向者选定的联系方式
- 意向者看到发布者此前授权的联系方式
- 双方完成一次真正的联系方式交换

### 8.6.4 信息可见结果

交换成功后：

- 意向者可见：
  - 发布者详细信息
  - 发布者授权的联系方式
- 发布者可见：
  - 意向者基础信息
  - 意向者详细信息（不打码）
  - 意向者本次主动发送的联系方式

## 10. 文案与交互原则

### 10.1 详细信息填写提示

在详细信息录入页需要明确提示：

- 详细信息只需要填写一次
- 填写详细信息是为了让对方更好地了解自己，减少来回沟通与信息不对称
- 未经授权，对方不能看到你的联系方式
- 即使对方可以查看你的详细信息，也不代表对方能直接看到你的联系方式

### 10.2 按钮前后的可见性提示

每一个关键按钮都要写清楚“点击后谁会看到什么”：

- 点击 `发送了解详情请求` 前
- 点击 `查看对方详细信息` 前
- 点击 `同意` 前
- 点击 `交换联系信息` 前

建议采用统一的信息提示模块：

- **对方将看到什么**
- **对方暂时看不到什么**

### 10.3 打码显示原则

打码展示应满足两个目标：

- 让用户知道对方是否认真填写了内容
- 不泄露具体文本、联系方式、可识别细节

建议做法：

- 保留字段标题
- 保留字数长度感知
- 具体文本替换为模糊块或部分遮罩

## 11. 状态机定义

建议按以下状态理解单条“了解详情”关系：

| 状态 | 说明 |
|------|------|
| `pending_request` | 意向者已发起请求，等待发布者处理 |
| `publisher_needs_detail` | 发布者点查看对方详细信息时，发现自己未完善详细资料 |
| `publisher_viewed_detail` | 发布者已查看意向者未打码详细信息（不含联系方式） |
| `rejected` | 发布者拒绝，且已填写理由 |
| `approved_detail_visible` | 发布者已同意，意向者可查看发布者详细信息，但不可看联系方式 |
| `contact_exchange_available` | 意向者可发起联系信息交换 |
| `contact_exchanged` | 双方完成联系方式交换 |

说明：

- `publisher_viewed_detail` 是 `同意 / 拒绝` 的前置状态
- `approved_detail_visible` 不等于 `contact_exchanged`
- 详细信息开放与联系方式交换是两个不同阶段

## 12. 业务规则与边界场景

### 12.1 基础规则

- 未登录只能看基础信息
- 收藏、点赞、了解详情必须登录
- 详细信息只填写一次
- 发布者不能给自己发“了解详情”请求
- 发布者同意 / 拒绝之前，必须先查看过意向者未打码详细信息
- 任何联系方式都不能在未授权状态下泄露

### 12.2 联系方式为空的场景

如果某一方此前没有填写任何联系方式：

- 在需要选择联系方式的弹框中允许即时补充
- 新增后应同步回写到该用户的详细信息中
- 未至少选择 1 个联系方式前，不允许完成该步操作

### 12.3 重复填写问题

- 详细信息不应要求用户对每个请求重复填写
- 同一个用户填写一次后，后续所有请求共用
- 后续只在联系方式选择与授权上做单次动作

### 12.4 拒绝后的处理

- 拒绝后该请求结束
- 是否允许再次发起，后续可单独定义
- 本期文档先不要求实现复杂的撤回、拉黑、重新申请策略

### 12.5 多项目 / 多卡片问题

当前需求重点在资料与授权流程，不强行定义“一个项目方可发布多少项目”。

MVP 建议：

- 可以先按“一个账号一个主展示对象”理解
- 多项目能力在后续产品迭代中再补充

## 15. 本次文档结论

本次重构的产品主线已经明确为：

- 平台存在两种角色：项目方 / 程序员
- 所有用户先录入基础信息，再在需要时录入一次详细信息
- 未登录用户只能看基础信息
- 收藏、点赞、了解详情必须登录
- “了解详情”是一个比收藏、点赞更高级、更醒目的授权型动作
- 发布者处理请求时，先看意向者基础信息与打码详细信息，再决定是否查看未打码详细信息
- 发布者必须先查看过未打码详细信息，才能同意或拒绝
- 同意后先开放详细信息，不直接开放联系方式
- 联系方式需要第二次动作“交换联系信息”后才真正互通
- 前端将从 Taro 重构为 Next.js v16，后端继续使用 NestJS
